# ADR 0004: Contents API commit author and committer identity

- Status: Accepted
- Date: 2026-07-28
- Repository: `TakashiSasaki/git-hosting-service`

## Context

The initial implementation includes GitHub Contents API-compatible `PUT` and `DELETE` operations. Each operation creates a Git commit and therefore must supply both author and committer identities.

The service must balance GitHub-style author attribution with reliable attribution of the authenticated Principal that actually caused the service to publish the commit.

## Decision

The service MUST distinguish author identity from committer identity.

### Author

The request MAY provide an `author` object using the documented GitHub-compatible subset.

- When `author` is present and valid, the supplied author name and email are written to the Git commit.
- When `author` is omitted, the service derives the author from the authenticated Principal's configured commit identity.
- The supplied author represents the attributed originator of the content and is not treated as proof that the named person authenticated to the service.

### Committer

The committer MUST always be generated by the server from the authenticated Principal's configured commit identity.

- A client-supplied `committer` field is not accepted in the initial API subset.
- The authenticated Principal that performs the REST operation remains identifiable as the committer.
- The service MUST NOT allow a caller to replace the authenticated committer with an arbitrary identity.

### Validation

Author and committer names and email addresses MUST be validated before Git object creation. The exact validation limits and the Principal commit-identity storage model are separate decisions.

## Consequences

- The original author can be represented when one Principal commits content on behalf of another person.
- The actual authenticated actor remains recorded as the committer.
- This is intentionally more restrictive than the full GitHub Contents API, which permits an explicit committer object.
- API documentation must clearly state that the implementation is a compatible subset rather than complete behavioral equivalence.

## Remaining related decisions

- how a Principal's default commit name and email are provisioned and edited;
- whether an author email must be verified;
- exact name and email validation rules;
- exact PUT and DELETE request and response fields;
- audit logging of the authenticated actor independently of Git commit metadata.
